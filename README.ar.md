# Bremen Environmental Exposure Pipeline

Pipeline بحثية بـPython تبني على ERA5 وSentinel‑2، وتنتج جدول تعرض بيئي لكل منطقة/يوم ولكل منطقة/سنة. تُدخل حدود Bremen وخرائط استخدام الأرض المحلية؛ لا تنزّل بيانات أو تستخدم حسابات أو مفاتيح تلقائياً.

## تشغيل المثال المكتمل

Python 3.9+، مع تفضيل 3.11. من مجلد المشروع:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m bremen_exposure.demo
```

يولّد المثال منطقتين مستطيلتين قرب Bremen وثلاثة أيام حرارة وصورة NDVI. **كل البيانات اصطناعية، والحدود ليست أحياء رسمية، والراستر ليس بدقة Sentinel‑2 الفعلية.** جميع جداول التعرض تحمل `synthetic=true`. لا تستخدم المثال كدليل على الوضع البيئي في Bremen.

المخرجات في `outputs/demo/`:

- `exposure_daily.csv` وParquet: مفتاح فريد `(zone_id, date)`؛ حرارة وتغطية مكانية وخضرة.
- `exposure_annual.csv` وParquet: مفتاح `(zone_id, year)`؛ ملخص الفترة المطلوبة داخل السنة، وليس بالضرورة سنة كاملة.
- `ndvi_zone_scene.csv`: متوسط NDVI وتغطية البكسلات الصافية لكل منطقة وتاريخ صورة.
- `exposure.gpkg`: طبقة `zone_year` لفتحها في QGIS؛ إسقاط EPSG:3035.
- `provenance.json`: الإعدادات، SHA‑256 للمدخلات، إصدارات المكتبات، وقت التنفيذ UTC.

## بيانات البحث الحقيقية

1. حدود Ortsteile أو Stadtteile من [GeoPortal Bremen](https://www.geo.bremen.de/online-dienste/geoportal-bremen-14419). اختر مدينة Bremen، وسجّل مستوى التقسيم وسنة الحدود، ولا تخلطها بولاية Bremen التي تشمل Bremerhaven. صدّر طبقة واحدة بصيغة GeoPackage/GeoJSON وبها معرف ثابت `zone_id` نصي؛ احتفظ بالأصفار الافتتاحية. افحص تداخل حدود المناطق في GIS؛ البرنامج يرفض الهندسة غير الصالحة ولا يصلحها بصمت.
2. ERA5 `2m_temperature` ساعي بصيغة NetCDF من [ECMWF/Copernicus](https://www.ecmwf.int/en/forecasts/dataset/ecmwf-reanalysis-v5). اختر شبكة تغطي كامل الحدود مع هامش؛ مثال صندوق `[53.35, 8.35, 52.9, 9.15]` بترتيب شمال/غرب/جنوب/شرق، ويجب مراجعته مقابل حدودك بما فيها الأجزاء المنفصلة. حمّل كل ساعات فترة التحليل. يدعم المحول `t2m` بوحدة K وأبعاد `time` أو `valid_time`، و`latitude`, `longitude`. يجب اختيار عضو ensemble أو `expver` قبل الإدخال إن وجدا. يدعم أيضاً ERA5-Land بالشكل نفسه؛ سجّل المصدر الفعلي.
3. Sentinel‑2 **L2A**: B04 وB08 على الشبكة نفسها، وSCL (يعاد إسقاطه بأقرب جار). استخدم metadata المنتج لتحديد scale وBOA offsets؛ لا تفترض القيم من تاريخ المشهد وحده. انظر [المعادلة الرسمية](https://sentiwiki.copernicus.eu/web/s2-products) و[تصنيف المشهد](https://sentiwiki.copernicus.eu/web/s2-processing). توحّد tiles لنفس اليوم قبل إعداد manifest، وتقصّها إلى مجال الدراسة بهامش مناسب قبل التشغيل لتقليل التكلفة.
4. خريطة [Urban Atlas](https://land.copernicus.eu/en/products/urban-atlas?tab=land_coverland_use) كاملة التغطية، تضم جميع الفئات وليس الخضراء فقط. في إعداد 2018: `14100` حدائق/خضرة حضرية و`31000` غابات. نسبة الخضرة هنا تعريف تشغيلي لهاتين الفئتين؛ لا تشمل كل زراعة أو حدائق منزلية. فئات 2021 مختلفة للخضرة الحضرية؛ راجع [دليل 2021](https://library.land.copernicus.eu/products/Urban_Atlas_CLMS_UA2021_LULC_PUM_v1.html) وحدّث `green_codes` و`class_column` والسنة. سجّل المصدر والترخيص وتاريخ التنزيل محلياً.

```bash
.venv/bin/python -m bremen_exposure.prepare era5 data/era5.nc data/era5_daily

# مثال فقط لمنتج metadata فيه offset=-1000 وquantification=10000:
.venv/bin/python -m bremen_exposure.prepare sentinel \
  data/B04.jp2 data/B08.jp2 data/SCL.jp2 data/sentinel/ndvi_20230702.tif \
  --scale 0.0001 --red-offset -1000 --nir-offset -1000

.venv/bin/python -m bremen_exposure.pipeline config/research.json
```

للمنتجات المصححة أو harmonized استخدم offsets الخاصة بها لتجنب التصحيح مرتين. الإدخال يجب أن يكون DN أو reflectance خطية كما تحددها المعاملات؛ محول Sentinel يستخدم المعاملات الصريحة ولا يطبّق scale/offset المخزنين في الراستر تلقائياً. DN=0 مستبعد كـnodata. عند reflectance حقيقية استخدم `--scale 1` وoffset=0 مع مراجعة قناع nodata.

عدّل `config/research.json` حسب حقولك وفترتك. المسارات فيه نسبية لمجلد config؛ مسارات manifest نسبية لمجلد manifest. `ndvi_manifest` اختياري ويمكن حذفه عند غياب صور مناسبة.

`data/sentinel/ndvi.csv`:

```csv
date,path
2023-07-02,ndvi_20230702.tif
2023-07-12,ndvi_20230712.tif
```

محوّل ERA5 ينتج `climate.csv` تلقائياً. ويمكن إدخال GeoTIFFs يومية من مصدر آخر:

```csv
date,variable,path,unit
2023-07-01,tmean,20230701_tmean.tif,C
2023-07-01,tmax,20230701_tmax.tif,C
2023-07-01,tmin,20230701_tmin.tif,C
```

القيم المسموح بها للمتغير `tmean,tmax,tmin` والوحدة `C,K`. يتطلب كل ملف band واحدة وCRS صحيحاً وnodata معلناً. يطبق القارئ scale/offset المخزنين في GeoTIFF. لا تخلط حرارة سطح الأرض مع حرارة الهواء.

## الحساب وضبط الجودة

- المساحات في إسقاط أوروبي متساوي المساحة EPSG:3035. نسبة الخضرة = مساحة اتحاد المضلعات الخضراء المتقاطعة مع المنطقة ÷ كامل مساحة المنطقة؛ لا يحدث تكرار لمساحة المضلعات المتداخلة.
- تغطية استخدام الأرض = مساحة المنطقة المتقاطعة مع اتحاد **كل** الفئات ÷ مساحة المنطقة. التغطية الأقل من `minimum_coverage` تجعل `green_fraction` مفقودة؛ تبقى `green_area_m2` مساحة الخضرة المرصودة فقط.
- الحرارة وNDVI متوسطان موزونان بمساحة تقاطع كل بكسل صالح مع المنطقة، مع تحويل مساحة التقاطع إلى EPSG:3035. تستبعد nodata وNaN، وتُحجب النتيجة عند التغطية الأقل من الحد. لا توجد إعادة تحجيم توحي بدقة حرارة أعلى. الطريقة دقيقة عملياً على حدود البكسلات لكنها بطيئة للصور الكبيرة؛ قصّ البيانات إلى Bremen أولاً. حدود الخلايا الجغرافية تتحول كمضلعات مستقيمة الأضلاع؛ لا يجري تكثيف منحنياتها جيوديسياً.
- ERA5: يوم UTC، يتطلب 24 ساعة صالحة **لكل خلية**. الناقص يبقى مفقوداً. Tmin/Tmax هما أصغر/أكبر **العينات الساعية**، وقد يفوّتان القمم بين الساعات. للتواريخ المحلية أو الربط بأحداث صحية مؤرخة بتوقيت Europe/Berlin، يجب تعديل التجميع مع معالجة أيام DST ذات 23/25 ساعة؛ التحويل الحالي ثابت UTC ويُذكر في مصدر الجدول.
- الأيام الحارة: Tmax ≥30°C، وفق [تعريف DWD](https://www.dwd.de/DE/service/lexikon/Functions/glossar.html?lv3=101162)، مطبق هنا على أقصى العينات الساعية. `warm_minimum_days` يحسب Tmin اليومية ≥20°C؛ لا يُسمى ليالي استوائية لأنه لا يستخدم نافذة ليلية مستقلة.
- لا تُحوّل الأيام الناقصة إلى صفر. عدد الأيام المتجاوزة يبقى **عدداً مرصوداً فقط**؛ استخدمه مع عدد الأيام الصالحة. المتوسطات ونسب التجاوز تُحجب عند نقص التغطية الزمنية. `expected_days` هو طول الفترة المطلوبة داخل السنة.
- Sentinel: يُقبل SCL=4,5,6 فقط (نبات/أرض عارية/مياه)، وتُستبعد الظلال والسحب والثلوج والمجهول. NDVI=(B08−B04)/(B08+B04) بعد تصحيح reflectance، مع استبعاد القيم السالبة والمقام غير الموجب. قناع SCL وحده لا يضمن خلو كل التلوث؛ قد تحتاج cloud buffering أو مراجعة بصرية حسب الدراسة.
- `ndvi_scene_mean` متوسط متساوي الوزن لمتوسطات المشاهد المقبولة داخل الفترة والسنة؛ ليس مركباً موسمياً median لكل بكسل. قد يتأثر بانحياز توفر الصور الصافية وتوقيت الالتقاط. احتفظ بعدد المشاهد والتغطية عند التحليل.

## الاستخدام مع بيانات الصحة

اقرأ [قاموس المتغيرات](DATA_DICTIONARY.md) قبل الدمج. للنتائج اليومية ادمج بمفتاح المنطقة والتاريخ مع توحيد أساس التوقيت. للملخصات ادمج بالمنطقة والسنة وبالفترة نفسها. يمكن بناء lag للحرارة داخل كل منطقة بعد إعادة الفهرسة اليومية؛ لا تجعل lag يعبر مناطق مختلفة أو يعوض المفقود بصفر.

الجداول تصف التعرض المكاني العام، ولا تقيس التعرض الشخصي أو تثبت علاقة سببية. لا ينتج البرنامج مؤشراً مركباً صحياً بأوزان مفترضة. دقة [ERA5 الأصلية ~31km](https://confluence.ecmwf.int/pages/viewpage.action?pageId=673339992) و[ERA5-Land ~9km](https://www.ecmwf.int/en/forecasts/dataset/ecmwf-reanalysis-v5-land) قد تعطي قيماً متشابهة لأحياء كثيرة؛ NDVI لا يحوّلها إلى قياس حرارة محلي. سنة استخدام الأرض ثابتة وواضحة في الجدول؛ اختيار 2018 مع حرارة 2023 يحتاج تبريراً أو تحليل حساسية. لا تحوي المخرجات أعداد السكان؛ كل المتوسطات موزونة بالمساحة وليست بالسكان.

## إعادة الإنتاج

`requirements.txt` يحدد الاعتماديات و`requirements-lock.txt` يسجل البيئة التي اختُبرت هنا (Python 3.9/macOS ARM؛ قد تختلف إصدارات المنصات الأخرى). محولا ERA5 وSentinel ينتجان سجلات مصدر `preparation.json` و`*.tif.json`. أضف مسارات هذه السجلات اختيارياً إلى `preparation_records` في config كي تُضمّن في provenance النهائي. مدخلات البحث والمخرجات المولدة وبيئة Python مستبعدة من Git؛ الكود والإعدادات والاختبارات والوثائق ونتائج المثال النصية في `examples/` محفوظة في commit.
